# Demo 打磨了半年，玩家却没来：独立游戏该如何安排 Playtest、Demo 与新品节？

一款游戏的 Demo，值得花多长时间打磨？

以笔者自己的游戏开发经历来看，**越早推出可以用于验证游戏核心玩法的Demo一定是越好的** ，而当时我们并没有意识到这一点，而花了大量时间去打磨细节，虽然说让游戏的品质的到了一定的提升，但是相比于价值更大的宣发，现在看来其实是不值的。

从现在回看这段经历，笔者发现问题其实并不只是“宣传做晚了”。更早之前，团队就应该分清楚：当前版本究竟需要用于验证玩法，还是已经能够承担吸引玩家的任务？

Steam 提供了 Playtest、Demo 和 Early Access（抢先体验，简称 EA）几种不同方式。它们看起来都能让玩家提前接触游戏，却对应着不同的目的。分不清这些区别，就容易把测试包当成宣传材料，把 Demo 当成缩小的正式版，甚至把尚未成立的玩法直接放进付费 EA。

在笔者看来，独立团队不一定缺少继续打磨游戏的耐心，**更容易缺少的是对阶段的判断** ：哪些问题需要尽早交给玩家验证，哪些体验必须在公开前完成，以及什么时候才适合使用新品节这类集中曝光机会。

## 都是提前给玩家玩，Playtest、Demo 和 EA 到底差在哪里？

如果只按完成度理解，Playtest、Demo 和 EA 很容易被排成一条开发进度线：先做粗糙的测试版，再做精致的试玩版，最后推出内容更多的抢先体验版。

这种理解并不准确。Playtest 完全可以很精致，Demo 也不一定比 EA 更小。笔者认为，更有用的区分方式，是看玩家为什么进入这个版本，以及开发者期待玩家做什么。

**Playtest 的重点，是帮助开发者找到问题。** 

Steam Playtest 是免费的测试工具，使用与主游戏关联、但相互独立的 App ID。常规报名入口位于主游戏商店页，开发者可以控制参与人数和开放状态；它没有独立商店页，也不提供用户评测。[1]

战斗手感是否成立、经营循环能否被理解、第一次进入游戏的玩家会在哪里卡住，都适合通过这种方式验证。这个阶段不必把每一项资源都做到最终品质，但需要让玩家能够接触到真正需要测试的部分。

开发者熟悉自己的游戏，知道任务顺序，也知道某个功能为什么暂时不可用。陌生玩家没有这些背景知识。内部测试能够顺利推进的流程，到了外部玩家手里，未必同样顺畅。

因此，笔者更看重具体的行为反馈，而不只是“挺好玩”这样的评价。玩家第一次停下来是在什么位置，为什么反复打开同一个菜单，又为什么没有继续玩下去，这些信息往往更能指导修改。

Demo 的任务则有所不同。玩家下载试玩，通常不是为了帮助团队完成开发，而是**判断这款游戏是否值得关注** 。Steam 官方也明确指出，玩家会通过 Demo 作购买判断，因此试玩应具有足够质量，并且能够代表实际游戏体验。[2]

这也是笔者不赞成直接把“当前能运行的版本”叫作 Demo 的原因。任务走到一半无法完成，核心操作还需要开发者解释，界面里到处是不能使用的入口，这样的版本即使内容不少，也更适合继续测试。

**Demo 可以缺少后续地图、角色和系统，但已经开放的这一段，应当是完整的。** 玩家需要真正体验到游戏的吸引力，而不是通过未实现的菜单猜测未来会有什么。

至于 EA，区别更加直接：游戏已经开始出售了。

Steam 将 EA 定位为在持续开发中销售游戏，**当前版本应当已经可玩，并值得它目前的售价** 。官方同时强调，EA 不是预购，也不应被当成单纯为开发筹款的方式；**玩家应根据现有体验购买，而不是押注未来承诺** 。[3]

在笔者看来，“抢先体验”不能成为降低交付标准的理由。玩家可以接受内容尚未做完，却不意味着应该付费帮助团队寻找游戏究竟哪里好玩。如果核心玩法仍未验证，现有内容也不足以支撑售价，就应该先解决这些问题。

EA 也不是独立游戏的必经阶段。如果游戏已经基本完成，只剩最后的 Bug 测试，Steam 的建议是继续测试，而不是为此进入抢先体验。[3] 一个准备长期扩充系统的游戏，与一个依赖完整剧情的一次性体验，也需要分别考虑提前销售是否合适。

## Demo 应该做到什么程度？少一点内容，未必是坏事

公开 Demo 最容易陷入的纠结，是“还不够好”。美术还能优化，视频还能重剪，系统还能增加，某一段体验也总有继续调整的空间。

因为有了前一段完整开发游戏的经历，让笔者对这种心态有了更具体的认识。将近半年的打磨并非毫无价值，但如果改进主要围绕团队和熟人已经发现的问题展开，就仍然可能遗漏陌生玩家的体验，也无法回答市场是否真正对游戏感兴趣。

因此，笔者并不认为第一款游戏的 Demo 必须投入多少个月，也不赞成笼统地说“打磨半年一定不值得”。项目规模、玩法结构和已经获得的反馈各不相同。**更值得警惕的，是把公开的条件设成一个永远不会到来的“足够完美”** 。

判断 Demo 是否准备好，**首先要看玩家能否独立完成体验** 。

一个简单的测试办法，是邀请没有接触过项目的人试玩，而开发者尽量不作提示。如果必须不断解释“这里先点一下”“这个功能还没做”“接下来应该去另一边”，就说明版本尚未把必要信息传达给玩家。

其次，**Demo 要让核心玩法完整发生** 。经营游戏不能只教玩家认识菜单，却没有让玩家经历经营的结果；动作游戏不能只展示移动和场景，却没有代表性的战斗；强调角色关系的游戏，也不应让试玩全部停留在基础操作上。

笔者认为，**Demo 最值得投入的，是让这一段体验真正成立，而不是尽可能多地加入内容** 。少开放一个系统，可能不会影响玩家理解游戏；开放一个尚未接好的系统，却可能破坏整段试玩。

稳定性同样需要划清底线。公开版本不必以“零 Bug”为前提，但启动失败、频繁崩溃、任务卡死、存档损坏和关键文字无法阅读，都是应优先解决的问题。音量、分辨率、输入方式等基础功能，也不能因为“只是 Demo”就被忽略。

**Steam 审核通过不代表质量测试已经完成。** 官方明确说明，包体审核不是完整 QA，不会检查或找出大多数 Bug。[4]

另一个值得注意的问题，是开发者有时会把最有辨识度的内容全部留给正式版。避免剧透当然合理，但如果玩家还没体验到卖点，试玩就结束了，也很难期待他们主动想象完整版会有多好。

在笔者看来，Demo 应让玩家理解为什么值得继续玩，同时保留后续内容，而不是单纯展示一段最容易完成的前期流程。

时长也应服从这个目标。新品节没有统一的 Demo 长度要求。[4] 对某些游戏，一段紧凑体验已经足够；对另一些游戏，则需要更多时间才能体现系统变化。为了凑时长增加重复劳动，并不会让试玩更有说服力。

结尾应明确告诉玩家试玩已经结束，并提供主游戏商店页入口。Steam 官方提供了从 Demo 内打开主游戏商店页的方法。[2] 相比突然中断，这样的结束方式更有利于把试玩兴趣转化为后续关注。

## 新品节只有一次机会，应该留到发售前吗？

Steam 新品节目前通常每年在二月、六月和十月举办，具体日期和截止节点以对应届次的官方页面为准。[4]

关于它，最需要记住的规则是：**一款游戏只能参加一次。这个限制针对的是游戏，不是每个 Demo 版本。** 换一个包体、重新做一段试玩，或者改成另一个版本名称，都不能获得新的参加机会。[4]

报名以主游戏为主体，**活动开始前必须有公开可玩的 Demo，Playtest 不能代替 Demo** 。[4] 提前进行 Playtest 或提前发布 Demo，则不会因此失去资格，Steam 也不要求试玩必须在新品节首发。[4]

还需要特别注意 EA 的时间。新品节面向未发售的游戏，**在活动前或活动期间进入 EA，同样会失去资格** 。准备未来进入 EA 的项目可以参加，但已经进入 EA 的项目不可以。[4]

因此，打算通过新品节为 EA 发售积累关注的团队，应当把活动放在 EA 之前，而不是等到正式版推出时再考虑。

至于选择哪一届，笔者仍然倾向于一个相对保守的建议：对以销售为主要目标、资源又有限的小团队，**优先考虑 Demo 已经成熟、发售计划相对明确时，距离发售较近的那一届** 。

原因并不复杂。活动带来的关注需要后续承接。如果玩家试玩后产生兴趣，项目却迟迟没有新消息，团队就还要投入精力维持期待。临近发售参加，更容易把活动后的宣传和销售安排衔接起来。

值得注意的是，**千万不要仅仅因为某一届报名即将截止，就把整个开发节奏压缩到活动日期之前** 。新品节能带来更多试玩者，却不会替团队修好引导，也不会让一个尚未成立的玩法自动变得有趣。

如果大量玩家在相同位置卡住，活动期间的工作就会从展示游戏，变成集中处理原本可以提前发现的问题，从而使问题大量暴露而让新品节起到完全的相反效果。对只有一次机会的小团队，这种安排尤其值得谨慎。

## 参加新品节，不应从开幕当天才开始准备

在笔者看来，较为稳妥的做法，是先让一批外部玩家接触游戏，找到影响体验的问题，再决定是否把这个版本带进新品节。**首次外部测试不宜与活动开幕重合。** 

这不意味着所有团队都必须按 Playtest、Demo、新品节的顺序完成一套流程。定向测试也能提供帮助。重要的是，在集中曝光前，团队已经获得过真实反馈，并有时间据此修改。

时间安排同样不能只看开幕日期。报名、商店素材、包体审核和媒体预览都有各自的节点。目前新品节通用文档给出的安排是：**希望 Demo 赶上媒体预览，应在活动前五周提交包体审核；只计划赶上活动开始，则应在活动前三周提交。** 具体仍以对应届次的时间表为准，并应预留重新提交的余量。[4]

媒体预览也不是一次私密的版本分发。希望媒体在这个阶段试玩，就需要提前公开 Demo，普通玩家届时也能玩。Steam 不保证媒体一定试玩或报道某个项目。[4]

活动期间，官方不建议同时开放 Playtest 分散玩家，而是建议将参与者集中到 Demo。[4]

笔者认为，观察活动效果时，愿望单与下载量之外，至少还应关注玩家是否启动成功、是否接触到主要卖点，以及在哪里退出。只有知道兴趣没有转化为继续游玩的原因，后续修改才有方向。

## 独立 Demo 页面值得开，但不是“只赚不亏”

Demo 是否需要独立页面，也是小团队经常需要取舍的问题。

Steam 允许 Demo 拥有独立商店页，也允许只在主游戏页提供试玩入口。独立页可以介绍试玩内容，并开放 Demo 用户评测；无论是否设置独立页，Demo 都没有自己的社区中心。[2]

笔者倾向于在条件允许时设置独立 Demo 页面，尤其是试玩范围能够清楚说明、团队也希望收集公开评价的项目。单独介绍试玩包含什么，通常比让玩家从完整版介绍中自行筛选信息更直接。

不过，这也意味着需要维护额外素材和描述。**页面标注的功能、语言和模式应对应 Demo，而不是把正式版计划中的内容都列上去** 。[2] 若团队资源有限，先完善主游戏页和试玩体验，比勉强再开一个信息不准确的页面更重要。

独立 Demo 页会提供通往主游戏的明显链接，帮助玩家添加愿望单或购买。[2] 但试玩下载与主游戏愿望单增长是不同指标，不能直接混为一谈。

页面与包体也并非必须同时发布。Steam 允许先公开 Demo 的“即将推出”页面，再发布可玩版本。[2] 在笔者看来，需要同步的不是两个按钮的发布时间，而是宣传承诺与玩家实际能获得的内容：**如果宣传说现在可以试玩，链接打开后就应该能玩；如果只是预告，就应说明开放时间** 。

另一个需要提前安排的功能，是 Demo 的愿望单通知。首次公开可玩后，开发者可以在两周内手动触发一次通知，提醒将主游戏加入愿望单的玩家试玩。**这个机会只能使用一次，关闭后重新开放不会重置，参加新品节也不会再获得一次。** [2][4]

因此，Demo 首发、通知、新品节和发售不宜各自独立安排。即便团队没有复杂的营销计划，也值得提前明确这几个节点如何衔接。

## 结语：什么时候公开，比继续打磨多久更值得讨论

最后总结一下：Playtest 用于发现问题，Demo 用于展示值得期待的体验，EA 则意味着当前版本已经开始接受付费玩家的判断。工具本身并不复杂，困难在于识别项目目前处在哪个阶段。

对于新品节，笔者的建议是**应该先让 Demo 经过真实玩家验证，再根据发售目标选择合适的一届** 。临近发售通常更便于承接关注，但前提始终是试玩已经能够承担这项任务。

对第一次做游戏的团队，继续打磨往往比公开接受陌生人的评价更容易。前者每天都有可见的工作，后者却可能带来不符合预期的反馈。但也正是这些反馈，能够帮助开发者判断：下一个月，究竟该继续增加内容，还是先解决玩家已经遇到的问题。
